4. Principes appliqués

  • Souveraineté des données — aucun CDN étranger, polices embarquées, aucun traceur publicitaire ; tout tourne sur le serveur en Algérie.
  • API d'abord — toute la logique est dans l'API /api/v1, utilisée à l'identique par le site et l'application mobile.
  • Mobile d'abord — chaque écran est vérifié à 360 px de large, en français et en arabe.
  • Règles côté serveur — floutage des profils, droits d'abonnement et Trust Score sont calculés par l'API, jamais par l'interface seule.
  • Activation progressive — chaque module s'active ou se coupe par feature flag depuis le back-office.
  • Privacy by design (loi n° 18-07) — consentements horodatés, export et suppression des données, journal d'audit.
  • Aucune dépendance obligatoire à une IA générative — AI MATCH et le chatbot fonctionnent par règles explicables.

4. Parcours d'une requête

  1. Le site ou l'app appelle https://gofix-digital.dz/api/v1/… avec le jeton Authorization: Bearer (accès de 15 min).
  2. aaPanel termine le HTTPS et transmet la requête au Nginx de GoFix, qui détermine l'IP réelle du client et ajoute les en-têtes de sécurité.
  3. FastAPI valide les données (Pydantic), vérifie l'identité, le rôle et le statut du compte (suspendu = refusé), applique les limites de débit.
  4. La logique métier lit et écrit dans MongoDB ; les actions sensibles écrivent une ligne dans audit_logs.
  5. Réponse JSON. Une erreur renvoie {"detail": "code_erreur"}, traduit par l'interface ; une erreur interne ne montre jamais de trace.
  6. Quand le jeton expire, l'interface le renouvelle automatiquement (rotation du jeton de rafraîchissement, réutilisation détectée et bloquée).

PRISE EN MAIN DÉVELOPPEUR

Installer, tester et faire évoluer le projet sur un poste de travail

1. Prérequis

  • Docker Desktop (Windows / macOS) ou Docker Engine + plugin Compose (Linux).
  • Git. Le dossier n'est pas encore versionné : créer un dépôt Git privé (GitHub, GitLab ou serveur interne) est la toute première action à faire.
  • Node.js 20 pour l'application mobile (et pour lancer le site hors Docker).
  • Un éditeur : VS Code recommandé.

2. Installation locale en 5 commandes

cp .env.example .env                    # puis renseigner JWT_SECRET, ADMIN_EMAIL, ADMIN_PASSWORD
openssl rand -hex 32                    # valeur pour JWT_SECRET
docker compose up -d --build            # mongo + backend + frontend + nginx
docker compose exec backend python -m app.seed   # référentiels + données de démonstration
# ouvrir http://localhost  (back-office : http://localhost/admin)

Bon à savoir

  • Le super-administrateur défini par ADMIN_EMAIL / ADMIN_PASSWORD est créé, ou son mot de passe réinitialisé, à chaque démarrage.
  • Le seed est idempotent : on peut le relancer sans créer de doublons.
  • La documentation interactive de l'API est disponible en local sur http://localhost/api/docs (masquée en production).

Garde-fous de production

Avec APP_ENV=production, l'API refuse de démarrer et explique pourquoi dans les logs si : JWT_SECRET fait moins de 32 caractères ou est un mot courant, ADMIN_PASSWORD est trop faible, FRONTEND_URL n'est pas en https, CORS_ORIGINS contient « localhost », Elle avertit (sans bloquer) si le paiement en ligne n'est pas encore paramétré, si les e-mails ou SMS restent en mode console ou si MongoDB n'a pas de mot de passe. Tant que SATIM n'est pas paramétré, les commandes d'abonnement répondent « paiement momentanément indisponible » : le mode simulé n'est jamais utilisé en production.

Après toute modification du .env : docker compose up -d (les conteneurs concernés redémarrent). Protéger le fichier : chmod 600 .env.

Si « grep -c avx » affiche 0

F.7 Reverse proxy et HTTPS dans aaPanel

  1. aaPanel → Website → site gofix-digital.dz (vérifier que www.gofix-digital.dz figure dans les domaines).
  2. Onglet SSL → Let's Encrypt → cocher les deux domaines → Apply, puis activer Force HTTPS.
  3. Onglet Reverse proxy → Add : nom gofix, URL cible http://127.0.0.1:8080, domaine envoyé $host.
  4. Onglet Config (fichier Nginx du site) : vérifier ou compléter le bloc du proxy comme ci-dessous, puis enregistrer.
client_max_body_size 10m;            # photos et pièces justificatives (jusqu'à 10 Mo)
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;   # indispensable : IP réelle des visiteurs
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 60s;
}

Pourquoi l'en-tête X-Forwarded-For est indispensable

Les limites anti-abus (connexion, mot de passe oublié, formulaires) fonctionnent par adresse IP. Sans cet en-tête, tous les visiteurs auraient l'IP du serveur et se bloqueraient mutuellement. Le Nginx de GoFix ne fait confiance qu'au proxy local, donc un visiteur ne peut pas usurper une IP.

G.1 E-mails avec Admail (Algérie Télécom)

Admail (admail.djaweb.dz/new2017) gère les boîtes du domaine gofix-digital.dz. GoFix envoie ses e-mails (réinitialisation de mot de passe…) via le serveur SMTP d'Algérie Télécom avec une boîte dédiée.

  2. Boîtes utiles en plus : contact@ (affichée sur le site), support@ (tickets), admin@ (compte ADMIN_EMAIL).
  3. Obtenir les paramètres SMTP sortants : le guide Admail ne les donne pas. Les demander au support (support@algerietelecom.dz) : nom du serveur SMTP, port (465 SSL ou 587 STARTTLS), authentification requise, limites d'envoi par heure ou par jour.
  4. Renseigner le .env : EMAIL_PROVIDER=smtp, SMTP_HOST, SMTP_PORT, SMTP_USER=no-reply@gofix-digital.dz, SMTP_PASSWORD, SMTP_FROM=no-reply@gofix-digital.dz, puis docker compose up -d.
  5. Tester avec « Mot de passe oublié » et vérifier la réception, y compris dans les courriers indésirables.
  6. Délivrabilité : demander à Algérie Télécom de confirmer les enregistrements SPF (et DKIM si disponible) du domaine.

Renouvellement de l'abonnement messagerie

Admail affiche une alerte 15 jours avant la fin de l'abonnement. Sans renouvellement, les boîtes s'arrêtent, ainsi que les e-mails de réinitialisation de mot de passe. À inscrire dans le calendrier de l'entreprise.

G.2 Paiement en ligne CIB / Edahabia (SATIM)

Fonctionnement dans GoFix

  1. L'utilisateur choisit une offre ; l'API crée une commande au prix fixé par le serveur et l'enregistre chez SATIM (register.do).
  2. Le navigateur ou l'app est redirigé vers la page de paiement hébergée par SATIM : GoFix ne voit jamais les numéros de carte.
  3. SATIM renvoie vers https://gofix-digital.dz/api/v1/billing/callback/satim ; l'API vérifie le statut directement auprès de SATIM (confirmOrder.do).
  4. Si le paiement est confirmé, l'abonnement est activé une seule fois, même en cas de retours multiples, et la facture PDF est générée.

Certification (espace cibweb.dz → « Certification sites web marchands »)

  1. Avoir un contrat de paiement en ligne avec la banque de l'entreprise (adhésion e-paiement CIB) ; la banque transmet les accès à l'environnement de test SATIM (URL, identifiant, mot de passe, terminal).
  2. Back-office (super-admin) → onglet Moyen de paiement : choisir « SATIM – CIB / Edahabia », environnement « test », saisir l'URL de l'API, l'identifiant, le mot de passe et le Terminal ID fournis par la banque, puis Enregistrer et Tester la connexion. Aucun redémarrage n'est nécessaire. Communiquer à la SATIM l'URL de retour affichée sur le même écran.
  3. Vérifier les pages exigées par la certification : CGV (/legal/cgv), mentions légales (/legal/mentions) et confidentialité (/legal/privacy), complétées avec les informations réelles de la société (raison sociale, RC, NIF, adresse, contact).
  4. Dérouler les scénarios demandés par SATIM (paiement accepté, refusé, annulé, carte invalide…) et fournir les captures et numéros de commande visibles dans le back-office → Paiements.
  5. Après validation, la banque fournit les accès de production : dans le même onglet, passer l'environnement sur « Production SATIM », remplacer l'URL, l'identifiant, le mot de passe et le terminal, enregistrer, tester, puis faire un premier paiement réel de faible montant.

Sécurité de l'écran « Moyen de paiement »

  • Réservé au super-admin ; chaque enregistrement et chaque test sont inscrits au journal d'audit, sans aucun secret.
  • Le mot de passe SATIM est chiffré en base et n'est jamais réaffiché : le laisser vide conserve celui qui est enregistré.
  • Le chiffrement utilise CONFIG_ENCRYPTION_KEY (ou, à défaut, JWT_SECRET) : si cette clé change, ressaisir le mot de passe SATIM — l'écran le signale.
  • « Tester la connexion » vérifie que le serveur SATIM répond et accepte les identifiants, sans débiter de carte ; seul un paiement de test complet valide toute la chaîne.
  • Le « paiement de test (simulé) » est impossible à sélectionner en production : il activerait des abonnements sans paiement.

Si l'ancienne version était déjà certifiée

La certification porte sur l'intégration technique du site. Comme la V1 est une nouvelle intégration, vérifier son statut dans l'espace cibweb.dz et, en cas de doute, demander à la SATIM si une nouvelle recette est nécessaire.

G.3 SMS (connexion par code)

Désactivé par défaut (flag auth_phone_otp). Pour l'activer : choisir une passerelle SMS algérienne avec API HTTP, puis renseigner SMS_PROVIDER=http, SMS_HTTP_URL, SMS_HTTP_TOKEN, SMS_SENDER_ID=GOFIX. L'adaptateur envoie un POST JSON {"to", "from", "text"} avec l'en-tête Authorization: Bearer <token> ; l'adapter si la passerelle attend un autre format (backend/app/adapters/sms.py). Activer ensuite le flag dans le back-office. Limites : 3 envois par 10 minutes et 5 essais par code.

G.4 IA générative (facultatif)

Le chatbot répond à partir de la FAQ, sans IA externe. Une reformulation par un modèle de langage est possible (LLM_PROVIDER=openai_compatible + flag chatbot_llm). Avant de l'activer, vérifier où le fournisseur héberge les données, au regard de la loi 18-07.

2. Audit de sécurité (octobre 2026)

Revue complète du code, de la configuration et des dépendances. 15 points corrigés, chacun couvert par un test automatisé. Les plus importants : usurpation d'IP permettant de contourner les limites, attaque par force brute répartie sur plusieurs IP, démarrage possible en production avec une configuration de développement (dont un paiement fictif), absence d'en-têtes de sécurité, droits excessifs des modérateurs sur les administrateurs, contrôle du type de fichier fondé sur la déclaration du client, effacement incomplet des comptes. 3. Loi n° 18-07 (protection des données personnelles)

  • Déclaration du traitement auprès de l'ANPDP avant l'ouverture ; le registre des traitements est exportable depuis le back-office (super-admin).
  • Pages légales à faire valider par un juriste algérien : mentions, CGU, CGV, confidentialité.
  • Droits des personnes : export et suppression accessibles depuis « Mon compte » (site et app).
  • Mineurs : consentement parental sous le seuil défini (minor_age_threshold) ; données pédagogiques minimales.
  • Conservation : durées définies dans data_retention_months.

4. Procédure en cas d'incident

  1. Isoler : couper l'accès public (désactiver le reverse proxy dans aaPanel) sans éteindre les conteneurs, pour conserver les traces.
  2. Conserver les preuves : docker compose logs > incident-$(date +%F).log, export du journal d'audit, sauvegarde de la base.
  3. Changer les secrets : JWT_SECRET (déconnecte tout le monde), ADMIN_PASSWORD, mots de passe MongoDB, SMTP, aaPanel, root ; faire régénérer le mot de passe marchand SATIM par la banque et le ressaisir dans le back-office (« Moyen de paiement »).
  4. Corriger, tester, redéployer, puis rouvrir l'accès.
  5. Informer la direction ; en cas de fuite de données personnelles, évaluer avec le juriste les obligations de notification.

APPLICATION MOBILE

Configurer, compiler et publier l'application iOS / Android

1. Principe

L'application (dossier mobile/) utilise exactement la même API que le site : mêmes comptes, mêmes données, mêmes règles. Le back-office reste sur le web. Identifiant : dz.gofix.app (Android et iOS). Schéma de lien profond : gofix:// (retour de paiement).

2. Configuration de production

  • EXPO_PUBLIC_API_URL=https://gofix-digital.dz au moment de la compilation (HTTPS obligatoire).
  • Côté serveur : MOBILE_APP_SCHEME=gofix.
  • Incrémenter version dans mobile/app.json à chaque publication.
  • Une fois l'application publiée, coller ses liens dans le back-office → Paramètres → app_store_url et play_store_url : l'accueil du site et la page /app redirigent alors vers les stores, sans redéploiement.

cd mobile

EXPO_PUBLIC_API_URL=https://gofix-digital.dz npx expo run:ios --configuration Release # Mac + Xcode requis
# Option cloud (facultative) : npx eas-cli@latest build --platform all

5. Notifications push et localisation

  • Notifications : écran d'explication puis autorisation du téléphone (une seule fois, après la connexion) ; le jeton de l'appareil est enregistré (push_tokens) et chaque notification du site (réponse, message, rendez-vous, abonnement) est aussi envoyée sur le téléphone. Toucher la notification ouvre l'écran concerné. Configuration Firebase / Apple : Guide d'installation, E.3b.
  • Localisation : facultative, approximative (position précise bloquée sur Android), demandée seulement quand l'utilisateur appuie sur « Détecter ma wilaya » ou « Près de moi ». L'API renvoie la wilaya la plus proche et ne conserve pas la position.
  • Profil : chaque compte peut modifier nom, e-mail, téléphone (à revérifier), wilaya, et ajouter une photo facultative (visible par l'interlocuteur dans la messagerie).

Les textes viennent des dictionnaires du site. Après toute modification côté web : npm run i18n:sync dans mobile/. Les textes propres à l'app sont dans mobile/src/i18n/mobile.js. Le passage à l'arabe redémarre l'app pour activer le RTL natif.
